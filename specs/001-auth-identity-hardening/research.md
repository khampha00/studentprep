# Research & Architecture Decisions: Slice 001 — Authentication, Identity Integrity & Secrets Hardening

**Feature**: `specs/001-auth-identity-hardening/spec.md` | **Date**: 2026-11-14

## 1. Adaptive Password & PIN Hashing (`PasswordEncoder`)

- **Decision**: Replace `NoOpPasswordEncoder` in `SecurityConfig` with an Argon2id-first `PasswordEncoder` backed by `Argon2PasswordEncoder.defaultsForSpringSecurity_v5_8()` (`bcpkix-jdk18on` 1.78 is already declared in `backend/pom.xml`), delegating read verification across `$argon2id$` and `$2a$`/`$2b$`/`$2y$` prefixes only and rejecting any unhashed or plaintext values.
- **Rationale**: `V2__Seed_Data.sql` already uses `$argon2id$v=19$m=16384,t=2,p=1$...` generated by `Argon2PasswordEncoder.defaultsForSpringSecurity_v5_8()`. A custom `PasswordEncoder` delegating `encode()` strictly to Argon2id and matching `$argon2id$` -> `Argon2PasswordEncoder` and `$2a$/$2b$/$2y$` -> `BCryptPasswordEncoder` handles bare Spring Security 5.8 Argon2 hashes (without `{argon2}` prefix) as well as BCrypt hashes if present, while guaranteeing zero plaintext comparisons.
- **Alternatives considered**:
  - `PasswordEncoderFactories.createDelegatingPasswordEncoder()` alone: expects `{argon2}` or `{bcrypt}` prefixes, which would break existing bare `$argon2id$` strings in `V2__Seed_Data.sql`.
  - Pure `BCryptPasswordEncoder`: weaker memory-hardness against GPU cracking on 5-digit PINs compared to Argon2id, and would break `$argon2id$` verification.

## 2. Student <-> User Identity Synchronization & Event Outbox Confidentiality

- **Decision**:
  1. Remove manual `student.setId(UUID.randomUUID())` in `StudentManagementService.createStudent` (let JPA/Hibernate assign `Student.id` cleanly) AND replace `User extends BaseEntity` (which inherits `@GeneratedValue(strategy = GenerationType.UUID)` from `BaseEntity`) with an explicit assigned `@Id private UUID id` on `User` implementing Spring Data `Persistable<UUID>` (with `createdAt`/`updatedAt` auditing fields), so `UserSyncListener` preserves `User.id == Student.id`.
  2. Hash student PINs in `StudentManagementService` **before** persistence and **before** publishing `StudentCreatedEvent`, `StudentUpdatedEvent`, and `StudentPinResetEvent`; change those event payloads to carry `pinHash` (and `pinResetRequired`) instead of plaintext PINs so Spring Modulith's `event_publication` table never contains plaintext credentials. Include `registrationNumber` on `StudentDeletedEvent` so `UserSyncListener` idempotently deletes both DB user record and Redis session/unlock keys.
  3. Update `CustomUserDetailsService` to treat `Student` existence and `pinResetRequired` as authoritative when loading `ROLE_STUDENT` identities, preventing any async `@ApplicationModuleListener` propagation window from allowing deleted students or pre-reset PINs to authenticate immediately after commit.
- **Rationale**: In Spring Data JPA `SimpleJpaRepository.save()`, entities extending `@GeneratedValue` with non-null IDs enter `EntityManager.merge()`, which executes an unnecessary `SELECT` and mints a new UUID during persist—causing `User.id != Student.id` and breaking `findById`/`deleteById` in `UserSyncListener`. Furthermore, Spring Modulith `@ApplicationModuleListener` runs asynchronously after transaction commit (`AFTER_COMMIT`), creating a sub-second window where `users` lags behind `students` unless `CustomUserDetailsService` validates live student state cleanly.
- **Alternatives considered**:
  - Removing the `users` table for students entirely: violates existing `V1__Init_Schema.sql` structure and staff/admin separation (`ADMIN-001` has no `students` row); keeping synced `User` rows (with `pinHash`) preserves clean separation while fixing UUID ownership and stale-login safety.
  - Synchronous `@EventListener` only without Outbox: weakens Modulith outbox durability per Constitution Principle I.

## 3. One-Time Random PIN Onboarding & Reset UX (Clarification Q1 = Option A)

- **Decision**:
  - Server generates cryptographically random 5-digit PINs via shared `SecureRandom` during `createStudent`, `processBulkCsv`, and `resetPin` (using `SecureRandom` for `generateRegistrationNumber` as well, removing duplicate `Random` logic in `CsvStudentImporter`).
  - Plaintext `oneTimePin` (or `newPin` on `/reset-pin`) is returned **only once** in the synchronous `POST` response JSON. `GET /api/v1/admin/students`, `GET /api/v1/admin/students/{id}`, `GET /api/v1/admin/students/export`, and `GET /api/v1/admin/students/{id}/slip` NEVER return plaintext PINs or hashes.
  - CSV export removes the `Login PIN` column and neutralizes CSV spreadsheet formula injection by prefixing values starting with `=`, `+`, `-`, `@`, `\t`, or `\r` with `'`.
  - Admin frontend renders the one-time credential receipt immediately inside the Bulk Import modal (with one-time CSV/print slip button) and Student Detail modal on PIN reset (with in-memory printable slip view via `window.print()`), warning admins that the PIN cannot be retrieved once dismissed. `RegistrationSlipGenerator.getRegistrationSlipPdf(id)` omits plaintext PINs and prints a redacted status note.
- **Rationale**: Matches Q1 Option A and SC-001 without storing recoverable credentials or introducing plaintext PIN leakage in re-downloads or browser logs.
- **Alternatives considered**: Admin-supplied custom PINs (prone to weak admin defaults) or forcing immediate student first-login password change inside a high-throughput CBT exam kiosk.

## 4. JWT Renewal, Token Type Separation, Same-Device Exam Resume & Logout Ownership (Clarification Q2 = Option A)

- **Decision**:
  1. `SecurityConfig` configures explicit `AuthenticationEntryPoint` (returning RFC 7807 `401 Unauthorized`) and `AccessDeniedHandler` (returning RFC 7807 `403 Forbidden`), eliminating expired-JWT `403` responses that previously prevented `frontend/src/App.tsx` silent refresh.
  2. `JwtUtil` stamps `token_type: "access"` on access JWTs and `token_type: "refresh"` on refresh JWTs. `JwtAuthenticationFilter` accepts only `"access"` tokens; `/auth/refresh` and `/auth/login` (`isSameDevice`) accept only `"refresh"` tokens.
  3. `AuthController.login` and `logout` set cookie path to `/api/v1/auth` (so both `/refresh` and `/logout` receive `refreshToken`), `HttpOnly(true)`, `SameSite` configurable (`Strict` default), and `Secure` configurable (`${COOKIE_SECURE:true}` in `application.yml`, `false` explicitly in local dev/test config).
  4. `AuthController.login` evaluates `hasFlaggedSession` (`403`), `pinResetRequired` (`403`), and `isSameDevice` (valid refresh cookie whose `jti` equals Redis `session:<UPPERCASE_ID>`) **before** rejecting active `IN_PROGRESS` exam sessions. Same-device re-login rotates `jti` cleanly to resume; cross-workstation login while `hasActiveSession` is true returns `409 Conflict` unless a one-time Redis grant `exam_unlock:<UPPERCASE_ID>` exists (created by `POST /api/v1/admin/students/{id}/unlock-session` which also deletes Redis `session:<UPPERCASE_ID>` and emits an admin audit record).
  5. `AuthController.logout` accepts `Authorization` access token and/or `refreshToken` cookie, extracts verified claims (`sub`, `jti`, allowing expired access tokens after HMAC signature validation), and deletes `session:<UPPERCASE_ID>` **only if** the caller's `jti` equals Redis `storedJti`.
  6. Frontend `App.tsx` removes spurious background `/logout` calls during session eviction (`code === 'SESSION_EVICTED'` or matching evicted detail message) and expired refresh failures, and triggers silent refresh cleanly on `401`.
- **Rationale**: Fixes blockers #2, #4, #5, #6 and satisfies Q2 Option A end-to-end without race windows or accidental eviction of the legitimate active workstation.
- **Alternatives considered**: Unconditional device takeover on re-login (weakens anti-cheating workstation lock during exams).

## 5. Brute-Force Rate Limiting & Lab-NAT-Safe Throttling

- **Decision**: Replace single-endpoint sync rate limiting with endpoint-aware Redis rate limiting (with bounded in-memory Caffeine/ConcurrentHashMap fallback if Redis is temporarily unavailable):
  - `POST /api/v1/auth/login`: per-normalized-identifier failure counter (max 5 failed attempts / 15 min window -> `429 Too Many Requests` with `Retry-After` header, cleared on successful login) PLUS generous per-client-IP ceiling (e.g., 60 attempts / minute, configurable via `security.rate-limit.*`) to tolerate 50+ legitimate candidates sharing a single exam-center NAT IP.
  - `POST /api/v1/auth/refresh`: per-IP ceiling (e.g., 30 requests / minute) and per-subject refresh cap (e.g., 15 / minute).
  - Preserve existing `/api/v1/exams/active/sync` rate limit (`10` / min per authenticated student).
- **Rationale**: 5-digit numeric PINs only have 90,000 combinations (10000–99999); strict per-identifier failure lockouts block PIN enumeration in <0.01% of keyspace (`5 / 90000`), while high per-IP ceilings prevent false lockouts across shared school routers.

## 6. Role Separation (`ROLE_ADMIN` vs `ROLE_SUPERVISOR`) & Production Fail-Fast Guards

- **Decision**:
  - Update `SecurityConfig` so `ROLE_SUPERVISOR` retains read-only monitoring/analytics access (`GET /api/v1/admin/analytics/**`, `GET /api/v1/admin/subjects`, `GET /api/v1/admin/questions`, `GET /api/v1/admin/students` list/detail/results) while all `POST`/`PUT`/`PATCH`/`DELETE` routes under `/api/v1/admin/**`, plus `/api/v1/admin/students/export` and `/api/v1/admin/students/*/slip`, require `hasRole("ADMIN")`. Restrict `/api/v1/students/**` and `/api/v1/student/**` strictly to `hasRole("STUDENT")`.
  - Parse `cors.allowed-origins` in `SecurityConfig.corsConfigurationSource()` into explicit allowed origins (rejecting `*` with `allowCredentials=true`) and explicit methods/headers.
  - Add `@ConfigurationProperties` / startup `ProductionSecurityValidator` (`@Profile("prod")`) failing startup if `JWT_SECRET` < 32 UTF-8 bytes or equals the dev sample key, `cors.allowed-origins` contains `*`, `ADMIN_BOOTSTRAP_SECRET` is unset/weak when bootstrap is required, or `S3_ACCESS_KEY`/`S3_SECRET_KEY` remain `minioadmin`.

## 7. Legacy Migration (`V16` / `V18`), Admin Bootstrap & Test Fixture Isolation (Clarification Q3 = Option B)

- **Decision**:
  - Preserve historical `V16__Revert_To_Plain_Text_Pins.sql` in the immutable Flyway migration folder so databases that already recorded `V16` in `flyway_schema_history` never fail Flyway checksum validation, and immediately neutralize it in **`V18__Harden_Credentials_And_Pin_Reset.sql`**:
    1. Idempotently rename `users.pin` -> `users.pin_hash` and `students.pin` -> `students.pin_hash`.
    2. Add `pin_reset_required BOOLEAN NOT NULL DEFAULT FALSE` to both `users` and `students`.
    3. Mark all existing `students` whose `pin_hash` is not a valid Argon2id/BCrypt hash (including `'12345'` created by `V16`) with `pin_reset_required = TRUE` and overwrite `pin_hash = '!LEGACY_INVALIDATED!'`; do the same for `ROLE_STUDENT` rows in `users`, and mark any unhashed `ADMIN-001` row as `'!ADMIN_BOOTSTRAP_REQUIRED!'`.
  - Change `spring.flyway.baseline-on-migrate` in `application.yml` to `${FLYWAY_BASELINE_ON_MIGRATE:false}` and enable `validate-on-migrate: true` in `backend/src/test/resources/application.yml`.
  - Add `AdminBootstrapRunner` (`ApplicationRunner` running after Flyway): checks `ADMIN-001` in `users`; if `security.bootstrap.admin-secret` (`${ADMIN_BOOTSTRAP_SECRET:}`) is provided, hashes and sets `ADMIN-001`'s `pin_hash` (in `prod` profile, rejects missing/weak secret if `ADMIN-001` still holds `!ADMIN_BOOTSTRAP_REQUIRED!` or if configured secret < 12 chars or in known weak set like `admin123` / `12345`).
  - Add `@Profile("!prod")` `NonProdTestFixtureSeeder` (optional, property-gated) outside Flyway migrations for local dev/Playwright smoke tests, keeping production migrations free of test student secrets.
- **Rationale**: Works identically for both brand-new databases (where `V16` runs inside the same initial migration batch right before `V18` immediately scrubs it before the app accepts traffic) and upgraded existing databases without breaking Flyway history checksums. Note: `.env` in the developer workspace should have its exposed keys rotated externally before any shared deployment.

## 8. Ingestion Asset Validation, `LlmStructuringService` Header Auth & `docling-parser` Hardening

- **Decision**:
  - `IngestionController.uploadAsset` + `S3Service`: validate non-empty, `<= 5MB`, exact allow-listed MIME (`image/png`, `image/jpeg`, `image/gif`, `image/webp`) AND binary magic bytes (`PNG`, `JPEG`, `GIF`, `RIFF+WEBP`), blocking SVG/HTML/JS/unknown files with `400 Bad Request` (`IllegalArgumentException` -> RFC 7807 ProblemDetail) or `415 Unsupported Media Type`, ignoring raw `originalFilename` and storing strictly under `diagrams/<uuid>.<ext>`. Derive returned public URL safely via configured `s3.public-base-url` (no naive string `.replace("minio", "localhost")`).
  - `LlmStructuringService` + `AsyncIngestionWorker`: pass Gemini key in HTTP header `.header("x-goog-api-key", geminiApiKey)` instead of URL query string `?key=...`, add an `ErrorSanitizer` helper redacting query keys/tokens (`key=[^&\s]+`, `x-goog-api-key`, `Bearer ...`, raw `geminiApiKey` value) before storing `job.setErrorMessage(...)` or logging via SLF4J.
  - `services/docling-parser/main.py`: require `X-API-Key` matching `DOCLING_API_KEY` via `hmac.compare_digest` (reject with `401`, fail-closed `503` if `DOCLING_API_KEY` env var is missing), enforce max upload size (`10MB` configurable) via streamed chunk reading (`413` on overflow), guard `file.filename` being `None` + validate `.pdf` + `%PDF-` magic bytes (`400`), close `pymupdf` document and unlink temp file inside `finally:`, omit tracebacks from HTTP `500` responses, add `GET /health`, and add `services/docling-parser/requirements.txt` + Spring `DoclingService` `X-API-Key` header (`@Value("${docling.api-key:}")`, `@Value("${docling.parser.url:http://localhost:8000}")`).
